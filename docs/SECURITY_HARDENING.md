# Security hardening and release checks

Updated 24 November 2026. This document describes the security changes in the
current working tree and the checks required before relying on them in Render.

## Changes

- **Uploads:** document, thesis, course-material, and profile-image uploads are
  checked against allowed extensions, declared MIME types, and file signatures.
  Non-image downloads use attachment disposition and `nosniff`.
- **CSRF:** unsafe requests authenticated by ambient access-token cookies
  require the cookie-backed CSRF token and `X-XSRF-TOKEN` header. The shared
  browser fetch wrapper obtains tokens from `/api/auth/csrf`. Bearer-only API
  clients remain compatible; Origin validation remains an additional check.
- **Content Security Policy:** scripts and styles are same-origin, except for
  the explicit Cloudflare Turnstile origins. Inline scripts, event-handler
  attributes, and inline styles are disallowed; the jsDelivr allowance has been
  removed. The shared action dispatcher uses a fixed allowlist and does not
  evaluate code. Continue escaping/sanitizing all untrusted values inserted
  into HTML templates; the dispatcher is not an HTML sanitizer.
- **Optional MFA:** production keeps MFA available with
  `MFA_REQUIRED_FOR_PRIVILEGED=false` and `MFA_REQUIRED_FOR_ALL=false`. Users
  may enable it for their own accounts. Startup fails if MFA is enabled but
  `MFA_ENCRYPTION_KEY` is missing or is not a Base64-encoded 32-byte key.
  Keep the key stable, private, and recoverable from the approved encrypted
  backup process. MFA setup QR codes are generated by the application and are
  never sent to an external QR service. Each setup request generates a fresh
  secret, replacing any unverified setup key; setup responses are not cached.
- **Authentication case policy:** passwords are verified exactly as entered and
  are not case-folded by active sign-in or password-management forms. Usernames
  and email addresses are trimmed and matched case-insensitively for account
  compatibility and reliable recovery. Roles and permission codes are derived
  and normalized server-side; they are never trusted from user-entered form
  values. Preserve entered casing for free-text profile fields.
- **Account email verification:** account emails are format-checked in request
  DTOs and browser forms. New accounts and account-email changes receive a
  one-time verification link; signing in remains available while verification
  is pending, but password recovery is sent only to verified account emails.
  The account-security page provides verification status and resend controls.
  Existing accounts are grandfathered as verified by the schema migration to
  avoid interrupting existing recovery access.

See [MFA recovery](./MFA_RECOVERY.md) for enrollment and support-recovery
requirements. Recovery controls and production key custody still require
target-environment acceptance.

## Render status and release gate

On 24 November 2026, Render reported deployment `dep-dc2nh4mc6qcc73fi3km0`
as `Deploy succeeded | Live`, using image/commit
`sha-e7a6f502caed9e180e9f1451ed267f030ae4d2af`. GitHub Actions run
[133](https://github.com/ciphernelson072/mit_portal/actions/runs/45383385603)
passed backend, MySQL migration, frontend, browser E2E, image-build, and
publication checks.

Post-deployment checks confirmed `/` and `/admin-login.html` returned HTTP
200, `/actuator/health` returned status `UP`, and the login response used the
strict CSP without `'unsafe-inline'` or `cdn.jsdelivr.net`. The served login
HTML had no inline scripts, event-handler attributes, or style attributes;
HSTS and `X-Content-Type-Options: nosniff` were present. The 23 November
observation of the prior image's permissive CSP is historical and was
superseded by this release.

An MFA account-security UI defect was subsequently reproduced from the
provided screenshot: the page's button styles set `display: inline-flex`,
overriding the browser's default display behavior for `[hidden]`. As a result,
the “Turn off” action could appear while MFA status was false, and “Verify and
enable” could appear before a setup secret existed. The server correctly
retains 403 responses for policy-restricted or enrollment-only actions. The
source fix scopes `display: none !important` to hidden descendants on the
account-security page, guards verify/disable actions in the UI, returns a clear
409 if verification is attempted without a pending setup secret, and bumps the
service-worker cache. Focused backend tests (96), frontend tests (29), and
JavaScript validation (41 files) passed; full CI, image publication, and
deployment remain pending. This explains the screenshot state but does not
replace testing the precise failed action against the live service.

These public checks do **not** establish authenticated sign-in, MFA enrollment
or recovery, email delivery, database isolation, or production readiness.

Before enabling users on the updated release:

1. For future releases, confirm the intended commit and change scope; run the
   repository CI gates and build the Docker image from that exact commit.
2. Verify the Render environment contains `MFA_ENABLED=true`,
   `MFA_REQUIRED_FOR_PRIVILEGED=false`, `MFA_REQUIRED_FOR_ALL=false`, and a
   persistent valid `MFA_ENCRYPTION_KEY`. MFA is opt-in per account. Do not
   copy secret values into source, logs, or chat.
3. Confirm the image tag/digest and commit shown in Render match the reviewed
   release. A successful Git push alone is not deployment evidence.
4. Confirm Render health reports `UP`. A sleeping Free instance may return
   503 while waking; wait for startup and then retry once rather than
   interpreting the interstitial as application readiness.
5. From the live service, inspect `/admin-login.html`. The CSP must include
   `script-src-attr 'none'` and `style-src-attr 'none'`; it must not include
   `'unsafe-inline'` or `cdn.jsdelivr.net`. The page and generated markup must
   contain no inline script blocks, event-handler attributes, or style
   attributes.
6. Confirm `GET /api/auth/csrf` returns a token and sets the CSRF cookie; verify
   cookie-authenticated unsafe requests without the matching token are
   rejected. Do not paste token values into logs or reports.
7. Test optional MFA enrollment, sign-in, recovery, and session revocation
   with approved synthetic accounts before broader access. The Render private
   MFA configuration and encryption-key value were not inspected by the
   unauthenticated checks above.

Render's image-based release publishes through the CI workflow on its configured
release branches. Review [Render deployment](./RENDER_DEPLOYMENT.md) before
publishing; the Render service may consume a Docker image rather than build the
uncommitted local working tree.
