1. System overview and trust boundaries

The MIT Student Information Portal is a Spring Boot web application. Static HTML, CSS, and JavaScript are served by the application; the browser communicates with Spring APIs. Authorization is enforced on the server for role and record ownership. Hiding a button in a page is not an access-control boundary.

Environment rules

  • Keep development, test, staging, and production databases and credentials separate. Verify the destination before any migration, import, reset, or restore.
  • Use synthetic/test accounts in development and the current Render Free service. Never seed sample/demo accounts into a shared or production database.
  • Render managed PostgreSQL is not a drop-in replacement for this MySQL-specific application. Select a supported MySQL-compatible service and confirm its networking/TLS requirements.
  • Do not expose a developer machine using router port forwarding, publish MySQL, or use a temporary tunnel as a production address.
  • Production changes need an identified release, tested migration order, a verified pre-change backup, an operator, and a rollback/recovery plan.

Common paths: gateway /; student sign-in /index.html; employee sign-in /admin-login.html; public site /public/index.html; health /actuator/health. Health confirms service readiness, not workflow acceptance.

TEST Label the environment in test accounts and operator notes. Avoid copying real student records into lower environments.

3. Local setup and verification

Prerequisites

  • Windows 10/11, Git, Docker Desktop for the simplest local run, and the repository checked out.
  • JDK 25 is required to build/run Java directly. Docker builds supply the Java runtime. The Maven Wrapper is included; a separate Maven install is not required.
  • For direct database testing, use a supported local MySQL 8.0 test instance; current MySQL-specific migrations may not work unchanged with other engines/versions.
  • Node.js/npm is needed for frontend/unit tests. Install dependencies with npm ci only if the local dependency directory is absent or out of date.

Recommended local Docker workflow

Open PowerShell in the repository root. Read .env.example, replace placeholders with unique local-only values in an ignored .env, then start the stack:

Copy-Item .env.example .env
# Edit .env locally. Never commit or share it.
.\run-sis.bat docker-up

Wait for the script's health check. Browse to http://localhost:8080/ for the local gateway. Shut it down with:

.\run-sis.bat docker-down
Destructive operation: .\run-sis.bat docker-reset removes the local Compose database volume. Do not run it unless the exact local test data can be discarded and any needed backup is verified. Never aim local commands at a shared/institutional database.

Test the source before sharing a build

.\mvnw.cmd -q test
npm ci
npm run build
npm run test:unit
.\ops\run-e2e.ps1

The isolated browser runner provisions its own test instance/database. Do not change its base URL to a production portal. Record command, commit, test counts, and failures; passing local tests do not equal live environment acceptance.

Change and deploy the image safely

  1. Identify the reviewed source commit and run the project's CI/build/test gates. Check the Docker Hub commit-specific tag exists and its digest is the expected published artifact.
  2. Back up the target database and required uploads. For an existing schema, review migration compatibility and rehearse against a protected copy first.
  3. Change the Render image to the exact immutable commit tag (or verify an intentionally configured auto-update to latest); do not rely on a Git push alone.
  4. Wait for Render to report the deployment live. Inspect sanitized startup logs for migration/configuration errors.
  5. Check health, login and role-specific smoke workflows, logs, email if in scope, and persistence. Capture the deployment ID, image tag/digest, time, and results.

5. First administrator and first login

Do not create a new administrator on the assumption the database is empty. First confirm which database the service uses and whether it already contains users. Never turn on bootstrap on a populated or shared database.

One-time bootstrap for a new empty database

  1. Confirm database identity, owner approval, empty/initial state, engine compatibility, and completed backup plan. Review the migrations included in the exact application artifact.
  2. Temporarily set INITIAL_ADMIN_BOOTSTRAP_ENABLED=true and supply a unique username, reachable email, and unique password (at least 12 characters; within application byte limits) in Render's private environment fields.
  3. Deploy and wait for application startup and health. Verify that exactly the intended administrator can sign in over HTTPS.
  4. Immediately set the bootstrap flag to false and remove the bootstrap username/email/password fields from Render. The database claim is one-time, but removing secrets is still required.
  5. Require the administrator to choose a personal, non-shared password and configure MFA only through the approved staged process.

No default account or default password should be assumed. The identity/temporary credential handoff must be through an approved private channel. Never place passwords in a PDF, source file, ticket, email campaign, or chat.

Account lifecycle

  • Create accounts only for approved people and assign the minimum role and permissions required for their work.
  • Use one account per person. Do not share administrator credentials or impersonate a user.
  • Confirm contact/recovery email ownership using the deployed verification flow where enabled.
  • On role change, departure, or suspected compromise, disable/restrict access through approved admin controls, revoke sessions where available, preserve required audit records, and follow institutional retention policy.
  • When a temporary password is used, deliver it privately and require the account holder to change it before portal data access. Emailing permanent passwords is prohibited.

7. Admissions and account lifecycle

Application-to-enrollment flow

  1. Academic owners confirm the active year, programme availability, application dates, required fields/documents, and admissions/privacy notice.
  2. Open only approved programmes for applications. Test a synthetic public application and confirm its receipt/status behavior. Avoid collecting sensitive documents or payment-card data through public forms.
  3. Admissions staff review eligibility and record the decision through the authorized workflow. Record an audit trail; never approve an application merely to create a login.
  4. For accepted applicants, confirm enrollment/account creation and the programme/year assignment. Verify the account exists and is linked to the correct approved record.
  5. When enrollment completes, the portal attempts required-course registration for the student's current programme semester in each open term for that academic year. Review the returned created/already-registered/skipped counts and any issues; missing instructors or sections, full sections, financial holds, and prior drops require staff review.
  6. If configured, send onboarding details through the approved verified email path. Provisioned accounts receive a temporary password and must change it before portal access. If email is unavailable, follow the private administrator handoff without exposing credentials in a response or report.
  7. Test the new student's first login, password change, sign-out, and account recovery with a test account before opening the process to real applicants.

Admissions operating checks

  • Confirm programme and application are in the intended academic year; deactivate or close offers when no longer approved.
  • Protect application-status lookups and verify applicant access does not reveal other applicants' records.
  • Review email delivery state separately from admission/account state. A successful account operation with failed email requires a controlled follow-up, not a second application or duplicate account.
  • Keep application documents private, restrict downloads, and follow records-retention periods.
  • Test duplicate applications, invalid/missing contact information, rejection, acceptance, and unavailable-email-provider paths using synthetic accounts.

8. Teaching, results, and corrections

Canonical routine grading path: Teacher assessment-component entry is the normal path. Administrator single-grade/file import, if available in the active release, is for authorized batch or exceptional entry only; imported records remain pending and require teacher component-mark completion and normal review.

Configure and submit marks

  1. An administrator configures the course's assessment structure before any component marks exist. Define each component, type, maximum score, required/optional status, and weights totalling exactly 100%. Marked structures may be immutable so historical marks retain their meaning.
  2. Assign an active teacher to the correct course and confirm student enrollment. The teacher opens only assigned courses and enrolled students.
  3. Enter component marks and submit them through the supported teacher workflow. The server validates component membership, duplicates, score bounds and required marks, then calculates totals/grade points and retake state. Missing marks are not equivalent to zero.
  4. An administrator authorized for grade review examines the assessment structure and marks. Review is recorded against the exact data state; a later change invalidates that review.
  5. Approve the appropriate academic result version, then publish that exact version as a separate step. Verify the version/status and student visibility using test accounts.
  6. Before official publication, student pages expose workflow status only where the deployed version supports it; marks, grade values, GPA, and return reasons must remain hidden. After publication, confirm only the correct student can see their official report.

Corrections, retakes, and appeals

  • For a correction to an approved result, use the authorized correction workflow and record the reason. The portal preserves the prior result/assessment snapshot; an assigned teacher makes the change through the standard submission path.
  • Re-review and approve the changed result, then publish the new version. Correction authorization alone does not publish a result.
  • Retakes are separate attempts. The application stores attempt linkage; institutional rules for which attempt replaces another for CGPA/credits must be approved and configured operationally. Do not assume a universal retake policy.
  • Grade appeals are separate from grade correction authorization. Use the appeal workflow only if present in the deployed version; institutionally define deadlines, consultation, escalation, decision authority, and relation to correction/republication.
  • Do not send marks through ordinary email or include marks in notifications unless an approved policy and implemented flow explicitly permit it.
Progression remains registrar-controlled: New admissions start in semester 1. Review the progression recommendation against approved required-course results, then update the student's current semester only after registrar approval. The update attempts required-course assignment for open terms; it does not automatically advance a student.

9. Student self-service

  1. Open the student sign-in page over HTTPS and sign in with individual credentials. Complete a required first-login password change before using protected pages.
  2. Review contact/profile details and verified recovery email; ask the authorized office to correct identity/programme data.
  3. When the correct term's registration window is open, select an available course section. Full sections and closed registration should be rejected. Confirm the student's own registration history.
  4. View grades and official reports only when the current results version is published. Do not treat a pre-publication status notice as a final grade or rely on cached data.
  5. Review fee balances and use only channels that Finance has enabled and tested. Submit bank-transfer references through the intended workflow, not through an unapproved public message or email.
  6. Use the portal's supported attendance dispute, grade appeal, service request, or message workflow where enabled. Keep requests factual and avoid posting passwords, MFA codes, or payment secrets.
  7. Sign out on shared devices. Contact the institution's published support route for account recovery; never share a one-time code or password with support staff.
Offline/PWA note: The service worker improves delivery of static application assets. It is not a backup, a substitute for current server data, or proof that cached account data is current. Do not treat the portal as an offline record system.

10. Fees and payment operations

Manual and provider-based payments

  • Finance owns fee schedules, due dates, waivers, settlement details, reconciliation, refund review, and segregation of duties.
  • New finance-created student charges begin as DRAFT. A finance-authorized administrator must approve a draft before it appears in the student's balance, reminders, or payment flow. Verify the student, description, amount and due date before approval.
  • Manual requests remain pending until authorized Finance staff verify and reconcile payment evidence. Match references and exact amounts against an approved bank/provider statement; preserve an audit trail.
  • Flutterwave Standard hosted checkout is implemented in source, but production readiness is not established by code alone. Keep it disabled until sandbox checkout, signature/webhook verification, retries, duplicates, delayed events, settlement and refund reconciliation are accepted.
  • Refund creation is a request, not proof money moved. A different authorized Finance user must complete/reject after external payment is verified; record the unique provider/bank refund reference.
  • Other payment destinations (including bank instructions, PayPal, Airtel Money, and MTN MoMo) may be configuration/UI destinations without a complete automated provider integration. Verify each channel's status before offering it. Direct card collection is disabled; never store card number, CVV, PIN, or one-time codes in this portal.

Minimum payment acceptance tests (sandbox/test accounts only)

  1. Create a test fee and confirm amount, currency, due date, and student ownership.
  2. Exercise initiation, success, failure, cancellation, timeout, invalid amount, and unknown reference.
  3. For a hosted provider, verify server-side transaction status, exact amount/currency/reference, webhook signature, retry, duplicate and delayed events.
  4. Confirm browser return or an unsigned webhook alone cannot mark the fee paid.
  5. Reconcile provider settlement report to portal allocations and test refunds with separate requester/approver identities.
  6. Confirm audit logs record the actor and action without logging credentials or card data.
Do not switch to live payment keys or publish public account numbers until the institution has approved the channel and finance has completed reconciliation, refund, settlement, dispute, and support procedures.

11. Email, messages, and announcements

Transactional email and account recovery

  • For the current Render Blueprint, use Brevo HTTPS API: MAIL_PROVIDER=brevo, enable mail only when approved, set the verified MAIL_FROM_EMAIL, and store BREVO_API_KEY as a Render secret.
  • SMTP support exists in source but Render Free blocks outbound SMTP ports 25, 465, and 587. Do not switch to SMTP on Free; use the provider API or an explicitly approved SMTP relay that supports the target host.
  • After key rotation, test password-reset and verification email using an approved test inbox; verify sender, link destination, expiry, one-time use, delivery logs and support procedure. Never paste recovery links or tokens into chat.
  • Password-reset and verification endpoints intentionally use generic public responses to reduce account enumeration. Provider acceptance does not prove receipt. Never use an email response to disclose whether an account exists.
  • Admissions/onboarding emails may contain a one-time temporary password when configured; never send permanent passwords. Verify forced first-login change and private fallback before using real accounts.
  • Notification email is queued for eligible opted-in users. Failed deliveries are retried after 1, 5, and 30 minutes following the initial failure; review the admin dashboard's Email Delivery Activity panel for recent attempts and exhausted failures. A retry status is not proof of inbox receipt.
  • Grade and announcement emails depend on explicit user opt-in and valid profile contact addresses. Event-triggered email is distinct from in-portal notifications. Bounce/retry monitoring and target-inbox delivery still require acceptance.

Messages, campaigns, and notifications

  • Use recipient selection and audience targeting only as intended by the active release. Administrators must review recipient scope before sending a campaign; campaigns can send individually to many recipients.
  • Use test recipients first. Confirm the sender, recipient count, audience filter, content, and partial-failure report. Retry only identified failed recipients after verifying the previous outcome.
  • Do not place sensitive academic, financial, identity, or health details in bulk announcements or unsecured email.
  • Some service requests, leave requests, attendance disputes, appeals, and correction events currently use in-app alerts rather than email. Do not promise email notifications for those events without confirming implementation and policy.
  • Messages/attachments remain subject to retention, access, and export policies. Confirm that file links remain private and expire/access-check as designed.

12. Security, privacy, and access control

Credentials and privileged access

  • Keep database, JWT, payment webhook, Brevo, Flutterwave, MFA, and bootstrap secrets only in an approved secret manager/Render secret field. Never commit .env, paste a key into a guide, or include credentials in a screenshot.
  • Use distinct least-privilege database/application accounts. Do not use database root in a hosted service.
  • Give each operator a unique account; review administrator and finance permissions periodically. Only an authorized ADMIN should assign/revoke role permissions.
  • Each user account supports one active session. A new sign-in invalidates the previous session; users can revoke sessions from Profile > Security. Test this with two browsers and avoid shared accounts.
  • Rotate credentials suspected of exposure promptly. Keep signing keys stable unless following a planned rotation procedure because rotation can invalidate sessions or callbacks.
  • Keep secure cookies and HTTPS enabled. Restrict CORS to exact approved HTTPS origins and operational endpoints to authenticated administrators/approved monitoring networks.

MFA policy and recovery

MFA and privileged-role enforcement are off by default in the reviewed Blueprint. Before enabling:

  1. Approve the scope (administrators/finance-privileged accounts), enrollment schedule, helpdesk identity proof, independent approval, incident logging, and lost-device recovery.
  2. Generate and store a persistent Base64-encoded 32-byte MFA_ENCRYPTION_KEY in the secret manager. Back it up using the institution's encrypted key-custody process and test decrypting a non-production seed.
  3. Enable MFA first without mandatory enforcement. Enroll privileged users; verify login, challenge, refresh, session revocation, key restore and recovery.
  4. Production defaults to optional MFA with MFA_REQUIRED_FOR_PRIVILEGED=false and MFA_REQUIRED_FOR_ALL=false. Each user may enable it in Account Security; existing enrolled accounts remain protected until they disable it. Never promise recovery paths not supported by the source.

Privacy and student records

  • Obtain institution-approved privacy notice, lawful purpose, collection minimization, retention/deletion/legal-hold policy, complaint/support route, and named privacy owner before real data.
  • Inventory database, files, backups, exports, email provider, logs, monitoring and support copies. Apply access controls and retention/deletion across all copies.
  • Do not use production personal data in tests, tickets, screenshots or demonstrations. Use synthetic identities and redact identifiers from diagnostics.
  • Restrict downloads and exports to legitimate authorized scope. Verify student-owned and teacher-assigned-course boundaries using dedicated test accounts.
  • Review institution-approved public admissions/contact/social/privacy content before enabling applications.

13. Routine operations and monitoring

Daily operator routine

  1. Check Render deployment state, health, recent restarts, memory/storage capacity, application errors, and provider/database connectivity. Inspect sanitized logs; do not export secrets or personal records.
  2. Review urgent login/recovery, admission, student/teacher request, security, and system-status queues with least privilege.
  3. Finance reviews pending payments and refunds against external statements; require separation between requester and approver where policy requires it.
  4. Academic administrators review pending grade/appeal queues. Publish only reviewed, approved, intended result versions.
  5. Check email provider delivery/failure events and recent campaign summaries. Follow up using test-safe, recipient-specific procedures.
  6. Check backup freshness, latest artifact/checksum, storage capacity, and alert state. A status marker alone does not prove a restore.
  7. Review automated fee/grade deadline reminders and attendance-risk alerts. Fee and grade reminders run daily at 09:00 and attendance-risk alerts at 09:30 in APP_AUTOMATION_TIME_ZONE (default Africa/Nairobi); verify the intended timezone and investigate delivery failures.
  8. Record operator, time, environment, release, queue/action outcome and sanitized incident/ticket reference.

14. Releases, migrations, and rollback

Release procedure

  1. Start from a reviewed source change and identify its exact commit. Ensure the intended Render branch/image source is confirmed rather than inferred from an old record.
  2. Run required backend, migration, frontend and browser tests in CI. Review test failures and artifacts; do not bypass gates to publish a Docker image.
  3. Record the commit-specific Docker tag and digest. A mutable latest tag is not adequate release identity by itself.
  4. Review database migrations against a disposable copy using the actual engine/version. For an existing database, take and validate a backup and perform a data-preserving-copy rehearsal. Never treat a clean disposable database as evidence that an existing database is safe.
  5. Coordinate backup of database and uploads, release window, operator/approver, compatibility plan and rollback/recovery conditions.
  6. Deploy the identified image to staging/test first. Confirm live health and authenticated critical workflows with synthetic accounts.
  7. Record deployment ID, image digest, migration version, health, critical smoke outcomes, provider outcomes, and any exceptions.
  8. For production, obtain explicit institutional approval before enabling real data/users or switching provider credentials.

Rollback and schema compatibility

There is no universally safe automatic rollback across database migrations. Do not redeploy an older image blindly after schema changes. The previous application may not understand the new schema, and restoring an old database can discard newer writes.
  • Prefer a forward fix when the schema/data state is compatible and the recovery plan supports it.
  • Only application-rollback when the previous image explicitly supports the current schema and migration state.
  • If restoring database and files is necessary, coordinate a write freeze/downtime and restore both from a consistent verified recovery point.
  • After recovery, validate login, role boundaries, academic/finance data, file download, audit history, database schema, and service health in the target environment.

15. Backups and recovery

Render storage boundary: The current Free service uses ephemeral /tmp/uploads. A paid Blueprint disk mounted at /var/data persists uploads across restarts but does not back up the external database. A single attached disk is not shared storage for horizontal scaling. Establish independent database backups and upload backup/restore before real records.
Restore safety: Restore scripts overwrite or create data in the selected destination. Rehearse only to a newly created disposable database/path first; verify the checksum and target identity. Do not paste a production connection string into an example command or run a restore against an active database without explicit approval and a written recovery plan.

What must be protected

  • Database contents and schema/migration history.
  • Uploaded files and a mapping to the database records that reference them.
  • Required encryption/signing key material and recovery instructions, stored separately in approved encrypted secret management.
  • Configuration and immutable application artifact/digest. Never include secret values in general backup bundles.

Requirements for a valid operational backup

  1. Choose an institution-approved, encrypted, access-controlled off-host destination with tested retention and data-residency rules.
  2. Back up database and uploads on a coordinated schedule, with checksums and a documented completion/failure alert. Do not place backup files inside the upload folder.
  3. Store credentials for backup jobs through protected automation or secret management; never put passwords in command arguments, scripts, or logs.
  4. Test restoration in a new disposable database and empty staging path. Verify checksum, Flyway history, application startup, representative synthetic records/files, and owner/ACL behavior.
  5. Measure recovery time (RTO) and recovery point (RPO), document data loss window, owners, escalation, and approval before any production incident.

Repository backup tools

The repository provides scripts such as ops/backup-mysql.ps1, ops/restore-mysql.ps1, ops/backup-uploads.ps1, and ops/restore-uploads.ps1; TiDB-specific dumpling/scheduler scripts are also documented. Read each script and its parameters before use. Backups created on a local workstation are not off-site disaster recovery.

16. Incident response

Possible compromised credential or unauthorized access

  1. Notify the designated security/portal owner through the approved incident route. Record timestamp, environment, suspected account/secret type, and sanitized evidence. Do not include the secret itself.
  2. For a leaked API/database credential, revoke or rotate it at the provider, update the deployment secret securely, redeploy/restart if required, and test the dependent flow. Do not rotate JWT/payment signing keys without the planned impact/coordination process.
  3. Disable/restrict affected accounts and revoke sessions using approved tools; preserve audit records and logs subject to privacy rules.
  4. Determine possible data exposure, exports, emails, files and provider events with authorized reviewers. Follow institutional legal/privacy notification policy.
  5. Restore service only after the risk is contained and monitoring/login checks pass. Record root cause, corrective action, and review owner.

Service outage, database issue, or failed release

  • Check Render deployment status and sanitized logs; compare deployed image/digest with the release record.
  • Check health, database availability/connectivity, schema/migration errors, storage fullness and provider status. Do not run ad hoc SQL or delete files as a first response.
  • If a migration is implicated, stop writes/deployment changes if safe, contact database/release owners, and use the rehearsed compatibility/recovery plan.
  • Communicate user impact through approved channels. Never promise a recovery time until the operator's measured RTO and current evidence support it.

Data loss or restore request

Obtain explicit database and institutional authorization. Identify the exact restore point and scope, estimate lost writes, preserve the current state where feasible, freeze writes, restore to a disposable environment for validation, then follow the approved cutover plan. Database and uploads must be treated as a coordinated set.

17. Acceptance and launch checklists

Go / no-go: If database isolation, data restoration, privileged recovery, data privacy, credential safety, or role boundaries are unverified, keep the deployment in test mode and do not load real institutional data.

Environment and account setup

  • Test/staging/production service, database, domain and account owners are named and separated.
  • Database engine, host, schema, user privileges, TLS and isolation are confirmed; no production/shared database is used for testing.
  • Initial admin was provisioned only on a verified empty database; bootstrap credentials removed and flag disabled.
  • Campus, faculty, department, programmes, terms, categories, staff, courses and sections were entered from institution-approved source data.
  • Roles and permissions were tested with one administrator, teacher, and student account without exposing another user's data.
  • First-login password change, sign-out/session invalidation and recovery procedures were tested with synthetic accounts.
  • A second sign-in invalidates the first session; Profile > Security session revocation is tested for the intended account.

Academic, admissions, and finance

  • One synthetic public application completed review/decision/account provisioning and private credential handoff.
  • Required and optional admission-document rules were tested with synthetic files; reviewer access and retention are approved.
  • Automatic required-course assignment was tested for an admitted student and an opened term; skipped/missing-instructor/section/capacity cases are reviewed, and progression remains registrar-approved.
  • Teacher course assignment and enrollment boundaries tested; marks, review, approval, publication, correction and report download tested against the intended database.
  • Institution-approved grading, retake, CGPA, award, appeal and correction policies documented.
  • Fees, manual reconciliation, provider sandbox, refund separation and settlement process accepted by Finance; unverified channels remain disabled.
  • New student fee charges remain hidden as drafts until Finance approval; reminders and email retry status were checked with synthetic accounts.
  • File upload/download authorization and survival after restart/redeploy verified on the actual durable target storage.

Security and operations

  • HTTPS, secure cookies, exact CORS origins, database network restrictions, secrets, log redaction and role boundaries confirmed.
  • Brevo key rotated and active Render secret updated; controlled password-reset/verification/onboarding email delivered to test inboxes.
  • MFA policy, encrypted key custody, privileged enrollment and account recovery tested before enforcement.
  • Database and uploads backed up off-host, checksums verified, restore rehearsed, retention/access controls approved, RPO/RTO measured.
  • Health, metrics access, central logs, alerts and escalation recipients tested.
  • Institutional privacy notice, admissions text, public contacts, retention and deletion, support hours, incident contacts, and accessibility requirements approved.
  • Named campus users completed critical student/teacher/admin workflows on supported devices/network; issues are resolved or formally accepted.
