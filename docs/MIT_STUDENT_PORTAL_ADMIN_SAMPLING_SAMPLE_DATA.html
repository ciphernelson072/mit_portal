1. Read this before entering anything

Isolated test database only. Do not enter these examples into production, a shared live database, or a real student/staff record. Use a disposable database and a test-only portal instance. Some actions publish announcements, send email, create finance records, change enrollment, or affect result visibility.
  • This workbook supplies example values; it does not change application code, configuration, permissions, or the database for you.
  • Use existing records if the test database already has the campus, department, programme, category, or course. Do not create duplicates or reuse a unique code.
  • Use the exact field and selection shown in the live form. The live form and server validation take precedence if a label or option has changed.
  • Enter passwords only into the password field. Generate a unique temporary password privately; never print, screenshot, export, share, or save it in this workbook. Do not enter a real MFA code.
  • Emails use the reserved .invalid domain so examples cannot be delivered. Do not send test messages to them. If a mail-delivery test is needed, use an inbox controlled by the test operator and explicitly approved for that test.
  • Phone values are blank when optional. Where a form requires a phone, use only a non-routable QA placeholder in a disposable database or a test number controlled by your institution; never invent or use a person's number.
  • Numeric IDs are generated by the database. Select the named record in a dropdown, or look up its real generated ID in the test portal before submitting an Operations Workspace form. Never type an example ID from another database.

Actions to skip unless deliberately testing them

  • Do not confirm a payment, refund, or reconciliation against a live provider. Use only a verified sandbox or a local test fixture.
  • Do not create or assign permissions as part of ordinary data entry. Use existing permissions and an authorized test administrator.
  • Do not activate a new academic year, open registration, transfer a student, deactivate an account, approve/publish results, or change a final status on a shared database.
  • Do not open registration, add a required curriculum course, change a student's current semester or lifecycle status to ACTIVE, transfer a student, restore an account, or release a student's final financial hold on a shared database; these actions can trigger automatic required-course assignments.
  • Do not send an announcement or bulk email outside the isolated test instance. Keep the recipient list to QA accounts.
  • Do not run a built-in demo seed as a substitute for this worksheet. Use the portal forms with the synthetic values below.

Recommended entry order

  1. Campus > faculty > department > programme; academic year > terms; required curriculum courses.
  2. Course categories > teacher account/profile > courses > course units > assessment structure.
  3. Sections > timetable > examinations.
  4. Student account/profile or public admission > programme enrollment > open registration window > review automatic course-assignment summary.
  5. HR, attendance, marks, fees, requests, accommodation, library, scholarship, and other optional workflows.
  6. Reports and exports last, after sample records exist.

Automatic required-course assignment and progression

  1. In Operations Workspace, create curriculum rows for QA-BSSE and the required QA courses. Use semester 1 and required true for QA-CS101; optional courses should be explicitly marked optional.
  2. Confirm each required course has an active instructor and at least one active section in QA Term 1. Registration also requires an active programme enrollment, an open registration window, available capacity, and no financial hold.
  3. Open the QA Term 1 registration window only in this disposable database. The portal attempts assignments for eligible active students in that academic year and reports assignments already present, new registrations, skipped items, and issues. Check the Admin Dashboard message/summary and correct missing instructor, section, capacity, or eligibility problems.
  4. New admissions begin in semester 1. Use the student-programme lifecycle controls to check the progression recommendation against approved passing results. A registrar must approve progression before staff update the current semester; the portal does not advance students automatically.
  5. After a semester update, the portal attempts required-course assignment for any open term in the same academic year. Review the returned issue summary instead of assuming every course was assigned.
Opening registration and updating a semester create course registrations. Do not test either action against shared or real student records.

Grades, approvals, and academic reports

  • For a normal workflow, the assigned teacher creates a draft, submits every required assessment component, and sends it for review. The administrator checks the marks, acknowledges the assessment review, and then approves.
  • A rejected grade requires a reason. Corrections to approved results require a separate authorization reason; retakes create a separate attempt and keep the original.
  • Academic report approval and publication are distinct actions. Publish only the exact approved results version; the workflow affects what the student can see.
  • For exceptional batch import only, download the portal's CSV template first. Its columns are studentId, courseId, gradeValue, gpaScore, and remarks. Use the actual generated student/course IDs and the current grade policy. Imported grades remain pending and are not the routine teacher-marking path.
  • A student grade appeal has a selected grade (hidden ID) and a required reason, for example QA-only request for teacher consultation on the synthetic result. The administrator records a required decision note. Approval of an appeal does not itself change a grade.

11. System controls, exports, and final checklist

What the Admin System Settings screen actually provides

  • Navigation to Academic Operations and Finance; the forms in those modules contain the academic and fee fields documented above.
  • Admin data export and CSV exports for Statistics, Users, Students, Teachers, Courses, Grades, Fees, and Audit.
  • An Email Configuration information card and a Send Test Email action. The card states email delivery is configured on the portal host, not in the browser. It is not a form for entering a key.
  • System health indicators for database, API, email, database backup, and upload backup. These are status displays, not sample-data fields.
  • Email Delivery Activity lists queued/recent notification attempts and exhausted failures. Failed delivery retries after 1, 5, and 30 minutes following the initial failure; email preferences still apply, and a successful provider response is not proof of inbox receipt.

Fee/grade deadline reminders run daily at 09:00; attendance-risk alerts run at 09:30 using APP_AUTOMATION_TIME_ZONE (default Africa/Nairobi). Set the grade submission deadline on a term only when testing reminders, use a controlled QA inbox for any opted-in email, and review in-app notifications and delivery status. Do not expect a reminder email without the applicable user preference and a verified mail service.

Keep secrets out of the workbook and browser forms. Never put a mail API key, database password, payment key, JWT secret, MFA seed, or production URL in sample data, chat, exported test fixtures, or screenshots. Host environment settings are operational configuration and are outside the sample records requested here.

For a test-email action, type only an approved QA-controlled inbox. The .invalid sample addresses in this guide are deliberately non-deliverable and should not be used as recipients.
